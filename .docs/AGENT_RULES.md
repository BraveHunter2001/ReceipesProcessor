# Правила работы агента с `.docs`

## 1. Назначение каталогов

| Роль | Основная папка | Результат работы |
|---|---|---|
| Аналитик | `analitycs/` | Анализ бизнес-проблемы и критерии, по которым можно поставить задачу |
| Разработчик | `tasks/` | План реализации, решения, результаты проверок и лог выполнения |
| Координатор/PM | корень `.docs/` | Реестр связей, статусы и статистика |
| Ревьюер | все `.docs/` | Проверка полноты, непротиворечивости и трассируемости |

Название `analitycs` является историческим и не переименовывается без отдельного решения.

## 2. Правила для роли аналитика

1. Сначала найти существующий анализ по проблеме; не создавать дубликат.
2. Создать документ из `templates/analysis.md` и присвоить следующий `AN-###`.
3. Описывать проблему через бизнес-эффект, пользователей, границы и измеримый результат.
4. Отделять факты от гипотез и явно фиксировать открытые вопросы.
5. Не писать код и не выдавать технический план за готовое решение. Технические ограничения можно зафиксировать как входные условия для разработчика.
6. Завершать анализ критериями готовности и рекомендацией: создать задачу, уточнить анализ или не реализовывать.
7. После создания или изменения анализа обновить `INDEX.md` и поле связанных задач.

## 3. Правила для роли разработчика

1. Перед началом открыть связанный `AN-###`; если анализа нет или он противоречив, вернуть задачу на уточнение.
2. Создать/обновить `TASK-###` из `templates/task.md`.
3. Не менять исходный анализ задним числом: новые технические решения и отклонения записывать в задачу.
4. Вести лог короткими датированными записями: действие, результат, проверка, блокер.
5. Фиксировать статус задачи и ссылку на коммит/ветку, если они известны.
6. Перед завершением проверить критерии готовности анализа и добавить фактический результат проверки.
7. Обновить `INDEX.md` и `STATISTICS.md` при переходе статуса.

## 4. Правила для координатора/PM

- Поддерживать одну строку на анализ и задачу в `INDEX.md`.
- Не считать задачу завершённой без ссылки на анализ, критериев и записи о проверке.
- Раз в неделю или после заметного изменения обновлять `STATISTICS.md`.
- Не смешивать бизнес-статус анализа со статусом реализации задачи.

## 5. Статусы

### Анализ

`draft` → `in-review` → `approved` → `implemented` или `cancelled`.

### Задача

`backlog` → `in-progress` → `blocked`/`in-review` → `done` или `cancelled`.

Если задача заблокирована, в логе обязательно указать причину, владельца следующего действия и условие снятия блокировки.

## 6. Минимальная трассируемость

Связь должна читаться в обе стороны:

```text
AN-001 (бизнес-анализ) ── реализуется в ──> TASK-001 (разработка)
```

В анализе используется `Related tasks`, в задаче — `Source analysis`, а в `INDEX.md` — отдельная строка связи. Одна бизнес-проблема может иметь несколько задач, но задача должна иметь один основной анализ.
