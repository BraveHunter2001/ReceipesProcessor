# Анализ и план завершения `paddleOcr`

Документ предназначен для агента-разработчика, который должен закончить Python OCR-сервис. Код в рамках этого анализа не изменяется.

## 1. Цель компонента

`paddleOcr` должен быть отдельным HTTP-микросервисом, который:

1. принимает изображение чека через `multipart/form-data`;
2. выполняет распознавание текста с помощью PaddleOCR;
3. возвращает распознанные строки, confidence и координаты найденных текстовых блоков;
4. работает локально на `localhost:8000`;
5. совместим с клиентом `Infrastructure/PaddleOcrClient.cs`.

Основное .NET-приложение уже ожидает endpoint:

```text
POST http://localhost:8000/ocr/receipt
```

Текущее состояние `paddleOcr/main.py` — только проверка CUDA и создание экземпляра `PaddleOCR`. HTTP-сервера, endpoint, чтения файла, вызова OCR и формирования ответа пока нет.

## 2. Что нужно доделать

### Обязательно

- Создать FastAPI-приложение.
- Добавить endpoint `POST /ocr/receipt`.
- Объявить входной параметр как файл с multipart-именем `file`.
- Проверять, что файл существует, не пустой и имеет поддерживаемый тип.
- Читать содержимое `UploadFile` в память или во временный файл.
- Передавать изображение в PaddleOCR.
- Преобразовать результат PaddleOCR в стабильный внутренний формат ответа.
- Возвращать HTTP 200 с JSON при успешном распознавании.
- Возвращать понятные HTTP-коды и JSON-ошибки для некорректного файла, неподдерживаемого типа, ошибки декодирования изображения и ошибки OCR.
- Запускать приложение через Uvicorn на `0.0.0.0:8000` или как минимум на `localhost:8000`.
- Инициализировать модель один раз при старте процесса, а не на каждый запрос.
- Использовать только GPU-режим. CPU fallback не реализовывать.
- При недоступной CUDA, несовместимом GPU runtime или ошибке инициализации GPU завершать запуск с понятной ошибкой; принимать OCR-запросы в CPU-режиме запрещено.
- Добавить health-check endpoint, например `GET /health`.
- Обновить `requirements.txt`: зафиксировать совместимые версии библиотек.
- Добавить инструкцию установки GPU-зависимостей и диагностики CUDA.

### Желательно

- Ограничить максимальный размер файла.
- Ограничить список MIME-типов: `image/jpeg`, `image/png`, `image/webp` при подтверждённой поддержке PaddleOCR.
- Проверять реальный формат изображения, а не только расширение и `Content-Type`.
- Добавить структурированное логирование времени обработки и количества найденных строк.
- Добавить graceful shutdown и корректное освобождение ресурсов.
- Вынести порт, язык и лимит размера файла в переменные окружения. Режим устройства не должен иметь значения `cpu`: сервис всегда работает с `gpu`.
- Добавить тесты endpoint на валидное изображение, пустой файл, неверный файл и отсутствие распознанного текста.
- Добавить Dockerfile или отдельную инструкцию запуска, если сервис должен работать независимо от окружения .NET.

## 3. Контракт запроса

### Endpoint

```http
POST /ocr/receipt
Content-Type: multipart/form-data
```

### Multipart-поле

Имя поля должно быть строго `file`.

Именно это имя отправляет C#-клиент:

```text
content.Add(streamContent, "file", fileName)
```

### Пример запроса через curl

```bash
curl -X POST "http://localhost:8000/ocr/receipt" \
  -H "Accept: application/json" \
  -F "file=@receipt.jpg;type=image/jpeg"
```

### Поддерживаемые входные данные

Минимально необходимы JPEG и PNG, потому что .NET-клиент фактически отправляет обработанное изображение как PNG и устанавливает `Content-Type: image/png`.

Важно: исходное изображение из Telegram может быть JPEG, но перед вызовом OCR оно преобразуется в PNG в `Application/Service/TextExctractor.cs`. Поэтому сервис должен принимать PNG независимо от имени файла.

Рекомендуемые ограничения:

| Ограничение | Рекомендация |
|---|---|
| MIME | `image/png`, `image/jpeg`; дополнительные форматы только после проверки PaddleOCR |
| Максимальный размер | например, 10–20 MB, значение сделать конфигурируемым |
| Пустой файл | отклонять с `400 Bad Request` |
| Повреждённое изображение | отклонять с `422 Unprocessable Entity` |
| Другой тип файла | отклонять с `415 Unsupported Media Type` |

## 4. Контракт успешного ответа

Ответ должен соответствовать моделям в `Infrastructure/PaddleOcrClient.cs`.

```json
{
  "success": true,
  "lines": [
    {
      "text": "МАГАЗИН ПРОДУКТЫ",
      "confidence": 0.9876,
      "box": [
        [10, 20],
        [450, 20],
        [450, 55],
        [10, 55]
      ]
    },
    {
      "text": "МОЛОКО 2 x 100.00",
      "confidence": 0.9412,
      "box": [
        [10, 70],
        [500, 70],
        [500, 105],
        [10, 105]
      ]
    }
  ]
}
```

### Поля ответа

| Поле | Тип | Обязательность | Требования |
|---|---|---|---|
| `success` | boolean | обязательно | `true` для успешного HTTP-ответа; рекомендуется `false` только в error-body, если выбран единый формат ошибок |
| `lines` | array | обязательно | Массив найденных текстовых блоков; при отсутствии текста — пустой массив |
| `lines[].text` | string | обязательно | Распознанный текст одной строки без лишнего `null` |
| `lines[].confidence` | number | обязательно | Число в диапазоне `0..1`, если значение доступно |
| `lines[].box` | array | обязательно | Четыре точки полигона в формате `[[x,y], [x,y], [x,y], [x,y]]` |

Клиент .NET использует только `lines[].text` и собирает его через перевод строки. Однако `confidence` и `box` должны быть возвращены для диагностики и будущего улучшения качества.

### Требования к порядку строк

PaddleOCR может возвращать блоки в порядке, зависящем от версии и параметров. Сервис должен отдавать строки в порядке чтения: сверху вниз, а для близких по вертикали строк — слева направо.

Если PaddleOCR уже возвращает корректный порядок, его можно сохранить. Если нет, нужно отсортировать результаты по координатам bounding box. Нельзя сортировать по confidence: это разрушит порядок текста на чеке.

## 5. Контракт ошибок

Рекомендуемый единый формат:

```json
{
  "success": false,
  "error": {
    "code": "INVALID_IMAGE",
    "message": "The uploaded file is not a valid image"
  }
}
```

Рекомендуемые статусы:

| HTTP | `code` | Ситуация |
|---:|---|---|
| `400` | `EMPTY_FILE` | Файл отсутствует или имеет нулевой размер |
| `413` | `FILE_TOO_LARGE` | Превышен лимит размера |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | Неподдерживаемый MIME или формат |
| `422` | `INVALID_IMAGE` | Файл не декодируется как изображение |
| `422` | `OCR_NO_TEXT` | Изображение валидно, но текст не найден; допустимо также вернуть `200` с пустым `lines` — решение должно быть единообразным |
| `500` | `OCR_ERROR` | Ошибка PaddleOCR во время обработки |
| `503` | `MODEL_NOT_READY` | Модель не инициализирована или недоступна |

C#-клиент при любом неуспешном статусе выбрасывает исключение и включает тело ответа в сообщение. Поэтому error-body должен быть коротким, безопасным и полезным для логов, без stack trace и секретов.

## 6. Интеграция с текущим .NET-клиентом

Текущая интеграция находится в `Infrastructure/PaddleOcrClient.cs`:

- URL зашит как `http://localhost:8000/ocr/receipt`;
- запрос отправляется как `multipart/form-data`;
- поле — `file`;
- MIME выставляется как `image/png`;
- имя файла по умолчанию — `receipt.png`;
- клиент ожидает JSON с `success` и `lines`;
- `lines[].text` объединяются через `Environment.NewLine`;
- `confidence` и `box` сейчас не используются в бизнес-логике.

Сервис нельзя реализовывать с полем `image`, `photo` или `upload`, если одновременно не меняется C#-клиент.

Отдельно проверить поведение при пустом `lines`: сервис должен вернуть валидный массив `[]`, а не `null`, чтобы клиент не падал и возвращал пустой текст.

## 7. Зависимости

В текущем `paddleOcr/requirements.txt` указаны:

```text
fastapi
uvicorn
python-multipart
--find-links https://paddlepaddle.org.cn
paddlepaddle-gpu
paddleocr
```

Этого недостаточно для воспроизводимой установки.

### Обязательные библиотеки

- `fastapi` — HTTP API;
- `uvicorn[standard]` — ASGI-сервер;
- `python-multipart` — разбор `multipart/form-data` и `UploadFile`;
- `paddleocr` — OCR pipeline и модели;
- `paddlepaddle-gpu` — единственный допустимый runtime Paddle.

### Дополнительные библиотеки

- `Pillow` — проверка и декодирование изображений, если будет использоваться PIL;
- `opencv-python-headless` — только если preprocessing выполняется в Python; сейчас preprocessing выполняется в .NET, поэтому добавлять без необходимости не нужно;
- `pydantic-settings` — удобная конфигурация из переменных окружения;
- `httpx` — только для интеграционных тестов или внутреннего health-check, не нужен для самого endpoint.

### Что нужно решить по PaddlePaddle

Сервис должен работать только через GPU. Нельзя оставлять неопределённый GPU runtime и плавающую версию `paddleocr`. Нужно выбрать и зафиксировать совместимую матрицу:

| Режим | Runtime |
|---|---|
| NVIDIA GPU only | `paddlepaddle-gpu==<совместимая версия>` + соответствующая CUDA/cuDNN |

Точные версии должны быть подобраны под целевую Python-версию, ОС, архитектуру и установленную CUDA. Их нельзя угадывать по текущему `requirements.txt`; разработчику нужно проверить официальную compatibility matrix PaddlePaddle/PaddleOCR и зафиксировать результат.

Для этого проекта достаточно одного GPU-файла зависимостей, например `requirements.txt` или `requirements-gpu.txt`. CPU-зависимость `paddlepaddle` добавлять нельзя, чтобы окружение не могло незаметно перейти на CPU.

### Проблемы текущего requirements-файла

- версии всех пакетов не зафиксированы;
- `paddlepaddle-gpu` без версии может установить несовместимый runtime;
- `--find-links https://paddlepaddle.org.cn` выглядит недостаточно конкретно для выбора нужного wheel и должен быть проверен для конкретной версии Python/CUDA;
- нет явной зависимости `uvicorn[standard]`;
- нет описания системных требований GPU;
- нет lock-файла или проверенного способа воспроизвести окружение.

## 8. Инициализация OCR-модели

Модель должна создаваться один раз при старте приложения. Нельзя выполнять инициализацию внутри каждого вызова `/ocr/receipt`, иначе каждый запрос будет повторно загружать веса и занимать GPU-память.

Нужно определить:

- язык: текущий код использует `lang="ru"`;
- устройство: только `gpu`; значение `cpu` должно считаться ошибкой конфигурации;
- включать ли angle classification для повернутых чеков;
- конкретную модель/конфигурацию PaddleOCR;
- где хранятся скачанные веса;
- что делать, если веса нельзя скачать при старте.

Для русскоязычных чеков `lang="ru"` является базовым требованием. Если ожидаются английские или смешанные чеки, нужно проверить поддержку смешанного языка и влияние настройки на качество, а не просто заменить значение без тестов.

Рекомендуемое поведение старта:

1. прочитать конфигурацию;
2. проверить выбранное устройство;
3. создать OCR engine;
4. выполнить лёгкую проверку готовности;
5. только после успешной инициализации принимать рабочие запросы.

Если модель не загрузилась или GPU недоступен, приложение не должно переходить на CPU. `/health` должен показывать неготовность, а рабочий процесс рекомендуется завершать с ненулевым кодом после понятной записи в лог.

Проверка готовности должна явно подтвердить:

- Paddle собран с CUDA;
- CUDA runtime доступен;
- обнаружено хотя бы одно совместимое GPU-устройство;
- PaddleOCR действительно создан с `use_gpu=True` или эквивалентным GPU-параметром используемой версии API.

## 9. Изображение и preprocessing

Сейчас preprocessing уже выполняется в .NET до отправки:

1. BGR → grayscale;
2. увеличение в 2 раза;
3. Gaussian Blur;
4. adaptive threshold;
5. PNG encoding.

Python-сервис не должен без необходимости повторно применять агрессивную бинаризацию: двойная обработка может ухудшить распознавание. Сначала реализовать OCR поверх входного PNG как есть, затем сравнить качество на наборе чеков.

При необходимости добавить preprocessing в Python, его нужно сделать опциональным через конфигурацию и проверить на цветных, наклонённых и низкоконтрастных чеках.

Также нужно учесть, что `TextExctractor` получает байты через `MemoryStream.GetBuffer()`. Это не часть Python-сервиса, но при интеграционном тестировании важно проверить, что в него действительно приходят только фактические байты изображения и что `Cv2.ImDecode` не получает лишний размер буфера.

## 10. Безопасность и устойчивость

Сервис локальный, но всё равно нужно:

- не сохранять загруженные изображения на диск без необходимости;
- удалять временные файлы в `finally`, если они используются;
- ограничить размер тела запроса;
- не возвращать содержимое изображения и stack trace в ошибках;
- не логировать бинарные данные и персональные данные чека;
- предусмотреть таймаут на стороне клиента или документировать максимальное время обработки;
- не запускать несколько тяжёлых inference одновременно без оценки GPU-памяти;
- ограничить concurrency или ввести очередь, если модель не поддерживает безопасный параллельный inference.

На стороне .NET timeout сейчас не задан явно для `PaddleOcrClient`, поэтому Python endpoint не должен зависать бесконечно. Желательно дополнительно изменить C#-клиент, но это находится вне задачи завершения `paddleOcr`.

## 11. Наблюдаемость

Минимальные логи Python-сервиса:

- успешная инициализация модели и выбранное устройство;
- версия Python, PaddlePaddle и PaddleOCR при старте;
- размер входного файла и MIME без персонального содержимого;
- время OCR-запроса;
- количество найденных строк;
- ошибки валидации и inference.

Рекомендуемые endpoint:

### `GET /health`

Проверяет, что процесс работает.

Пример:

```json
{
  "status": "ok",
  "model_ready": true,
  "device": "gpu"
}
```

### `GET /ready`

Опционально отделяет доступность процесса от готовности модели. До загрузки модели должен возвращаться `503`.

## 12. Проверки и тесты

Перед передачей задачи считать сервис готовым только после проверки:

1. `GET /health` отвечает успешно.
2. `POST /ocr/receipt` принимает PNG с именем поля `file`.
3. C#-клиент без изменений успешно десериализует ответ.
4. Ответ содержит `success: true` и `lines: []` или непустой массив.
5. Каждая строка имеет `text`, числовой `confidence` и четыре точки `box`.
6. Порядок строк соответствует визуальному порядку на чеке.
7. Пустой файл отклоняется предсказуемо.
8. Текстовый файл под видом изображения отклоняется.
9. Слишком большой файл отклоняется.
10. Повреждённый PNG/JPEG не приводит к падению процесса.
11. Ошибка OCR не завершает Uvicorn и не ломает следующие запросы.
12. Повторный запрос не загружает модель заново.
13. Inference действительно выполняется на GPU; при отсутствии CUDA, GPU или совместимого runtime сервис завершается с понятной ошибкой и не переключается на CPU.
14. Проверены как минимум русскоязычный чек, чек с латиницей, низкоконтрастный чек и чек с несколькими строками товаров.

## 13. Критерии готовности для агента-разработчика

Задача завершена, когда в `paddleOcr` есть рабочий запускаемый FastAPI-сервис, который без изменений клиента .NET:

- стартует на `localhost:8000`;
- имеет `POST /ocr/receipt`;
- принимает multipart-поле `file`;
- инициализирует PaddleOCR один раз;
- распознаёт PNG/JPEG-чек;
- возвращает согласованный JSON-контракт;
- корректно обрабатывает ошибки и ограничения размера;
- имеет health-check;
- использует зафиксированные совместимые зависимости;
- документирует только GPU setup, версии CUDA/cuDNN, драйвера и PaddlePaddle GPU;
- содержит минимальные automated или reproducible manual tests;
- не требует изменения `Infrastructure/PaddleOcrClient.cs` для базового сценария.

## 14. Вопросы, которые нужно закрыть до реализации

1. Целевая среда — Windows, Linux или Docker Linux?
2. Какая версия Python, драйвера NVIDIA и CUDA установлены на машине запуска?
3. Какой GPU и объём его VRAM доступны сервису?
4. Должна ли модель скачиваться автоматически при первом запуске или веса поставляются отдельно?
5. Нужен ли `lang="ru"` только для русского, или требуется смешанный русский/английский режим?
6. Что считать успешной обработкой изображения без найденного текста: `200 + lines: []` или `422 OCR_NO_TEXT`?
7. Какой максимальный размер фотографии допускается Telegram и сколько запросов в секунду ожидается?
8. Нужна ли авторизация, если OCR-сервис будет доступен не только на loopback-интерфейсе?

Если эти решения не приняты, агенту следует реализовать GPU-only baseline: русский язык включён по умолчанию, `paddlepaddle-gpu` и совместимые версии зафиксированы, запуск блокируется при недоступной CUDA, CPU fallback отсутствует, пустой результат возвращается как `200` с `lines: []`, а endpoint слушает только локальный интерфейс или явно документирует bind на `0.0.0.0`.
