# AN-003 — Повышение надёжности и сопровождаемости backend

**Status:** `approved`  
**Owner:** аналитик  
**Created:** 2026-11-07  
**Updated:** 2026-11-07  
**Related tasks:** `TASK-003`

## 1. Контекст и проблема

Backend сейчас сочетает HTTP endpoint-ы, доступ к EF Core/S3, Telegram-интеграцию и фоновые обработчики в небольшом количестве классов. `Application` напрямую зависит от `Infrastructure`, фоновые workers используют инфраструктурные детали, а обработка очереди не имеет claim/lock, ограниченных повторов и отдельного статуса ошибки.

Это затрудняет тестирование и повышает риск двойной обработки чеков, бесконечных повторов, утечек данных и orphaned-файлов в MinIO.

## 2. Цель и ожидаемый результат

Получить backend с явными слоями, устойчивой обработкой очереди, конфигурируемыми внешними интеграциями, стабильными API-контрактами и автоматическими тестами.

| Метрика | Текущее значение | Целевое значение | Способ проверки |
|---|---:|---:|---|
| Двойная обработка одного чека | не контролируется | исключена механизмом claim | integration-тест |
| Ошибка одного чека останавливает batch | возможно | не останавливает остальные | worker-тест |
| Application зависит от Infrastructure | да | нет | анализ project references |
| Конфигурация внешних URL/таймеров | частично hardcoded | options + validation | startup/integration-тест |

## 3. Область решения

### Входит

- baseline-тесты текущих API;
- нормализация options и DI;
- разделение Application/Infrastructure через интерфейсы;
- выделение use case-ов загрузки, чтения и обработки чеков;
- claim/lock, retry и `Failed` для фоновой обработки;
- ограничения upload, ProblemDetails и health checks;
- unit/integration/API-тесты;
- миграции для полей обработки и индексов.

### Не входит

- немедленное удаление Telegram-кода;
- изменение бизнес-правил OCR/LLM без отдельного анализа;
- публичная авторизация как часть первого этапа, но её отсутствие остаётся P0-риском перед production.

## 4. Требования и ограничения

- Не ломать существующие маршруты `/api/receipts` и upload без миграционного периода.
- Не редактировать применённые миграции; изменения оформлять новыми миграциями.
- Секреты хранить в User Secrets/environment/secret storage.
- Все внешние операции должны поддерживать cancellation, timeout и ограниченный retry.
- Antiforgery, временно отключённый для upload, вернуть после появления cookie-аутентификации.

## 5. Поэтапный план

1. **Baseline и безопасность (P0):** тесты API, лимиты файлов, единые ошибки, конфигурация Telegram/S3/OCR/Ollama, фильтрация владельца.
2. **Options и DI (P0/P1):** options-классы, `ValidateOnStart`, `IHttpClientFactory`, исправление lifetime и удаление ручного создания клиентов.
3. **Границы слоёв (P1):** интерфейсы репозитория, storage, OCR и parser в Application; реализации в Infrastructure; устранение ссылки Application → Infrastructure.
4. **Use case-ы (P1):** разделить текущий `ReceiptService` на upload, list, details, image и processing.
5. **Очередь обработки (P0/P3):** claim через PostgreSQL, промежуточные статусы, retry/backoff, `Failed`, `AttemptCount`, `LastError`, `LockedUntil`.
6. **API (P2):** вынести endpoint-ы из `Program.cs`, DTO, validation, `ProblemDetails`, correlation ID и health checks.
7. **Domain и БД (P1/P3):** timestamps, concurrency token, единые денежные типы, индексы и явное преобразование опечатки `TextExctracted`.
8. **Наблюдаемость и финальная проверка:** структурированные логи, метрики стадий, миграции на чистой и существующей БД, полный набор тестов.
